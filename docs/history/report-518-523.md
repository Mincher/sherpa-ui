## Your five choices

Each has my pick first. Where my thinking changed since I first asked, the revision is marked.

### 1. R2 — how a component joins its data when it is alone

Today only `sherpa-provider` turns what a component asks for (`static asks`) into a working connection. So a component bound alone with `bindSource` gets only part of its features:
- a filter bar shows no chips, and its Add list is empty;
- charts, metrics and the legend ignore their own settings, and the legend cannot filter;
- a grid heading lists only one page's values.

Your old rule 388 says "a grid is never wired by hand".

- **A (my pick):** move the provider's ask-to-connection code into one shared helper in `core/ui`. The provider calls it, so apps see no change. A component bound alone through the helper gets every feature. Rule 388 becomes "bind through the helper, never by hand".
- **B:** the provider stays the only join. "Alone" then means "with no other UI component" (no bar, shell or header).

**Revision (523):** A is a MOVE of the provider's existing code, not new code. That fits your 523 rule: only revise, refactor or cull.

### 2. R4 — the defaults that only the provider sets

Four defaults you ruled ON are written only by the provider. A component used alone still has the old behaviour:
- "Select none shows all data" (517);
- the heading Group button (500);
- heading buttons shown on hover (501);
- multi-field tags (490).

- **A (my pick, revised):** a DATA setting lives in the data layer, in the source, as I already did for `highlightAcross` in 520. "Select none shows all data" moves there, and each bound component reads it. A PRESENTATION setting (the heading Group button, hover buttons, tags) keeps its attribute, flipped, so that leaving the attribute off gives your default. That is 3 attribute renames, and Demos moves with them.
- **B:** leave them as they are.

**Revision:** I first offered "flip all four attributes". With your 523 rule (the data layer decides), the data setting belongs in the source instead.

### 3. U1 — every site of a customer ticked

In the panel, ticking every site of a customer picks the WHOLE customer. The bar's tree menu and the grid heading keep the sites as "some", as your 369 rule (Q1 A) says. So the same ticks filter different rows: the whole customer also matches rows with no site.

- **A (my pick):** "these sites", everywhere, the panel too: your 369 rule.
- **B:** "the whole customer", everywhere.

No revision.

### 4. U9 — Apply with only one end of a date range

A grid heading clears the field. A chip filters to that one day.

- **A (my pick):** it filters that one day, everywhere, as the chip shows it.
- **B:** it clears the field, everywhere.

**Revision (523):** under either choice, the rule lives in ONE place, the data layer (`filter-state.ts`), and the grid stops deciding it.

### 5. 521 — a press on a blue "info" value that a preset turned on

The plan for 521:
- a preset's conditions stay in the query, as your 510 rule says, but in a separate place on each field;
- each field keeps the mode the reader left it in, so nothing flips to Advanced;
- each value a preset turns on wears the blue "info" look, and its tooltip says "On by the preset ‹name›".

Choices:
- **A (my pick):** a press on an info value turns that preset off (all its fields). Its tooltip says so.
- **B:** the press does nothing; only the preset's own chip turns it off.

No revision.
