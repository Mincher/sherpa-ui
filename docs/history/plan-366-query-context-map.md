# Plan 366 — one QueryContext: the map

Will, 2026-10-20: one QueryContext per app Context, for every source and every
component in it. This is step 1: a read-only map of where the Query lives today,
every copy, and how sources relate. Five readers, one synthesis, two skeptics.
Line numbers are as of 2026-10-20 and will drift; the skeptics found some
citations off by a section (noted in §5).

## 1. Is the Query the one truth?

Mostly. Will is right about the design, but the build stopped half way. Each DataSource holds ONE Query, `#applied` (src/core/data/data-source.ts:194). On a local store the draft IS that same object (:200). It holds which scope holds each field, each field's reading and which saved filters are on, and it is the only place a filter is made (#recompose → #compileNow, :1436-1467). The written design says what Will says: "Controls are VIEWS of the Query … None of them holds an answer of its own" (docs/QUERY-DESIGN.md:56-58), and every control should only "READ its slice, REQUEST a change" (:286-296). But the controls are not pure views today. A chip's answer lives in its menu's DOM. The bar sends its WHOLE answer on every change (src/components/sherpa-quick-filter-toolbar/sherpa-quick-filter-toolbar.ts:1123-1141). The source takes that as the scope's new answer and CLEARS each field the report does not name (data-source.ts:703-704, reached from answerScope :2259-2277). It then draws the result back into every control over that scope, the sender too (data-source.ts:1134-1135, 1148-1164; src/core/data/source-binding.ts:191-197). That is a two-way loop, and it is why the code needs echo guards (the panel's #said, src/components/sherpa-filter-panel/sherpa-filter-panel.ts:149, 1655), stale-draw guards (the toolbar's #editedAt, toolbar.ts:1115-1120, 1328) and holds for answers that read empty for a moment (#pendingAnswers, toolbar.ts:907-908). Will's ruling B on 2026-10-13 kept the per-component doors (docs/TODO.md:1490-1491). Inside the source, three things still sit BESIDE the Query: `saved:<id>` parts made from an unscoped bar's own readings (data-source.ts:2310-2313); a whole filter set by hand with setFilter/setState, which clears the readings (:409-419, :518-525); and sort, group and search in #state (:146). So the Query is the one truth for which rows the FILTERS let through. It is not yet the one truth for what each control SHOWS and SENDS.

## 2. Many sources

One page has one source. Each DataSource has its own Query (data-source.ts:194). Under <sherpa-provider>, open() gives a page exactly one source, `{ [definition.id]: source }` (src/components/sherpa-provider/sherpa-provider.ts:312). The provider can hold several (`#sources`, :128). But then it gives no Views and no kept Query (:265), and only tests use two sources. No code copies a filter from one source to another, so there is nothing to sync between sources. Sources over the same remote store share ROWS through one StoreCache (data-source.ts:231), never filters. Storage copies (session, View drafts, saved Views, saved sets) go out one way and come back one way, by setQuery. So the two-way sync Will feels is not BETWEEN sources. It is between ONE source and the controls drawn from it: bar, panel, grid heading and legend.

## 3. Why 319 still matters

Yes, 319 still matters with one central truth. It is part of what keeps the truth central. In JavaScript, passing an object passes the same object. Nothing is copied. Before 319, the source kept the app's saved-filter object itself. So the app still held a pen that wrote straight into the truth and skipped the source's door: no recount, no event, no redraw (`declarePreset` now copies on the way in, data-source.ts:724-726). That is the "two owners" problem again, but hidden. One truth that two hands can change is not one owner. The way out is still open. `describe()` hands out the source's own preset objects (data-source.ts:772, 800), and only a "READ-ONLY" comment guards them (:746-748). The object also really travels. The bar keeps it (toolbar.ts:1359, then a shallow `{...def}` at :1506) and sends it back in every report (`get presets`, :1241-1246). In Will's ideal design, where every control only reads the one truth, this matters MORE: every reader gets the object, so each one would hold a pen unless what it reads is a copy or frozen. The same gap is still open on the busiest door. `write()` and `select()` keep `answerOf(reading)` (data-source.ts:566, 1126), which copies only the top layer (src/core/data/query.ts:172-176). So a control's `conditions` array becomes the Query's own, and the binder passes event details straight in (src/core/ui/bind-source.ts:217-226). Note: no user hit 319. It was found by reading the code, and no caller writes to these objects today (docs/TODO.md:8176-8180).

## 6. The two options it gave

**A: Make the controls draw-only (finish the Query design)** — its pick

Do what docs/QUERY-DESIGN.md §8 already says (:286-296). A bound control draws from the source and sends only a request for the one field it changed. Steps: (1) the bar sends one field's change, not its whole answer, so 'clear what is not named' no longer runs on chips; (2) lock every chip in a bound bar, so on/off comes only from the draw; (3) keep a superseded chip's old answer in the Query as a suspended reading; (4) one description per scope and one way to draw a bar (TODO 320); (5) drop the `saved:<id>` parts (320). After that the guards can go: the panel's #said, the bar's #editedAt and #pendingAnswers, #lower's overwrite, and the provider's two-frame mute. Will's B doors (setChipReading, columnClause…) can stay as thin calls to the source. A bar with NO source keeps its own answer, as it does now.

Cost: Large. It touches the toolbar, panel, grid heading, legend and provider, and many tests in sherpa-ui and Demos. It changes behaviour, so per TODO 320 it comes after 302/311 and Will's test run (docs/TODO.md:339).

**B: Keep two-way, but close every object door (finish 319)**

Copy on the way in at every door: write(), select(), apply, answerScope (copy `conditions` and `picked`), setState, setFilter and contribute. Copy or freeze what goes out from debugState, supersedeColumns and #draw. Add one unit test that writes to every object the source hands out and checks that the source did not change.

Cost: Small, about a day. The bench clone count rises a little (319 already moved */open from 7 to 10). It does NOT remove the two-way sync. It only makes sure nothing can change the truth except through the source. It can be done first, on its own.
