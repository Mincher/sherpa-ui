# Figma → Sherpa Token Contract

This document is the source of truth for how Figma Variables and DTCG token  
files are translated into Sherpa CSS custom properties by  
[generate-css-tokens.js](generate-css-tokens.js).

If you are **adding a new Figma variable**, **adding a theme**, or **renaming**  
**an existing token**, follow this contract. If the contract changes, update  
this document _and_ the generator together — they must stay in sync.

---

## 1\. Inputs

| Path | Format | Purpose |
| --- | --- | --- |
| `figma-tokens/figma-variables.json` | Figma | Primitives, Alias, Status, Density, component collections, plus `themes.{base,extended[]}` config. |
| `figma-tokens/{ThemeFolder}/Light.tokens.json` | DTCG | Per-theme Light-mode tokens. |
| `figma-tokens/{ThemeFolder}/Dark.tokens.json` | DTCG | Per-theme Dark-mode tokens. |

`themes` block in `figma-variables.json`:

```
"themes": {
  "base":     { "name": "Apex 2.0 Core",            "slug": "apex-2-core",     "folder": "Apex 2.0 (N-able Core)" },
  "extended": [
    { "name": "Apex 2.0 (N-able Data Protection)",  "slug": "data-protection", "folder": "Apex 2.0 (N-able Data Protection)" },
    { "name": "Classic",                            "slug": "classic",         "folder": "Classic" }
  ]
}
```

*   `name` — display label (used in CSS file headers and console logs).
*   `slug` — kebab-case identifier; drives the output filename (`sherpa-theme-{slug}.css`) and the `darkOverrides` key.
*   `folder` — directory under `figma-tokens/` containing `Light.tokens.json` + `Dark.tokens.json`.

## 2\. Outputs

| File | Generated by | Layer | Loaded |
| --- | --- | --- | --- |
| `tokens/sherpa-alias.css` | `generateAlias()` | `@layer tokens` | `@import` in `index.css` |
| `sherpa-status.css` | `generateStatus()` | `@layer tokens` | `@import` in `index.css` |
| `sherpa-fonts.css` | `generateFonts()` | `@layer tokens` | `@import` in `index.css` |
| `sherpa-components.css` | `generateComponents()` | `@layer tokens` | `@import` in `index.css` |
| `sherpa-theme-base.css` | `emitBaseAndDiffs()` | `@layer theme` | `@import` in `index.css` (always loaded) |
| `sherpa-theme-{slug}.css` (per theme) | `emitBaseAndDiffs()` | `@layer theme` | Runtime `<link id="sherpa-theme">` in HTML `<head>` |

`tokens/primitives.css` is **hand-maintained**, not generated.

### Theme base + diffs

`emitBaseAndDiffs(built)` runs after every theme's prop list has been built:

1.  Compute the intersection of `(propName, val)` pairs across every theme.
2.  Emit the intersection as `sherpa-theme-base.css` (declares `color-scheme: light dark` once).
3.  For each theme, emit only the props whose value differs from base.

Per-theme files therefore contain only the **diff**. Adding a new theme costs  
roughly one diff file (~80 lines) instead of a full token dump (~411).

## 3\. Naming Translation

Figma variables are translated to CSS custom properties through these rules,  
in order. See `sanitize()`, `apexToCSS()`, `contentToIcon()`, `refToVar()`.

### 3.1 Sanitisation (always)

`sherpa-ui/scripts/generate-css-tokens.js` `sanitize()`:

| Figma fragment | CSS fragment |
| --- | --- |
| `->` (data-viz arrow) | `-` |
| `/` (path separator) | `-` |
| (space) | `-` |
| Uppercase | lowercase |

### 3.2 Category remapping (Apex 2.0 themes)

`apexToCSS()` rewrites the category prefix before sanitisation:

| Figma prefix | CSS prefix | Notes |
| --- | --- | --- |
| `surface/status/` | `surface/context/` | Status surfaces become "context" surfaces. |
| `border/status/` | `border/context/` | Same. |
| `content/status/` | `text/context/` | Status content becomes context text by default. |
| `content/default/` | `text/default/` | Content → text namespace. |
| `content/primary/` | `text/primary/` | Same. |
| `content/inactive/` | `text/inactive/` | Same. |
| `content/active/` | `text/active/` | Same. |

Status-token rename: every literal occurrence of `critical` becomes `error`  
(`renameStatus()`). The Figma source uses `critical`; CSS public API uses  
`error` for OWASP-friendly semantics.

### 3.3 Icon variant

When a `content/*` token is referenced from the **Icon** axis, it is rewritten  
through `contentToIcon()` instead of `apexToCSS()`:

| Figma prefix | CSS prefix |
| --- | --- |
| `content/default/` | `icon/context/default/` |
| `content/primary/` | `icon/primary/` |
| `content/status/` | `icon/context/` |
| `content/inactive/` | `icon/inactive/` |
| `content/active/` | `icon/active/` |

Trigger this by passing `{ iconMode: true }` when calling `refToVar()`.

### 3.4 Reference resolution (`refToVar()`)

A Figma value beginning with `@` is a reference. Resolution order:

1.  **Primitive collection** (`@color/basic/...`, etc.) → `var(--core-{sanitized})`.
2.  **Alias collection** → `var(--sherpa-{sanitized})`.
3.  **Active theme collection** (Apex 2.0) → `var({apexToCSS()})` or `var({contentToIcon()})` for icon-mode.
4.  **Pattern inference fallback** — if the name begins with `color/basic/`, `color/extended/`, `border/{radius,stroke,dash}/`, `scale/`, `effects/`, `motion/`, `typeface/` → treat as primitive.
5.  **Default fallback** — treat as alias.

> Steps 4 and 5 exist for forward-compatibility with new Figma additions that  
> have not yet been re-exported into the lookup sets. They should rarely fire;  
> if they do, prefer fixing the export over relying on the fallback.

## 4\. Value Formatting

`formatVal(val, type, varName)`:

| Input | Output |
| --- | --- |
| `@`\-prefixed reference | `var(...)` via §3.4 |
| `rgba(...)` string | Trimmed to 2 decimal places; `.0)` → `)` |
| Other string | Pass-through |
| Boolean | `"true"` / `"false"` |
| Number, `type=FLOAT`, value 0 | `0` |
| Number, `varName.includes('letter-spacing')` | Unitless number (rounded to 3dp) |
| Number, `abs(val) < 1` | Unitless number (assumed multiplier) |
| Number (other FLOAT) | `{val}px` (rounded to 3dp) |
| Number (non-FLOAT) | `String(val)` |

## 5\. Mode (Light / Dark)

Per-theme tokens use the CSS [`light-dark()`](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark) function so a single property  
serves both modes. Required on `:root`:

```css
color-scheme: light dark;   /* declared by sherpa-theme-base.css */
```

Mode selection at runtime is done by overriding `color-scheme` on  
`document.documentElement` (`"light"`, `"dark"`, or `"light dark"`).

### When light/dark values diverge

| Token type | Diverges? | Generator behaviour |
| --- | --- | --- |
| Colour | Often | Emits `light-dark(LIGHT, DARK)`. |
| Non-colour (sizes, motion, etc.) | Should not | Emits **light** value and prints a console warning. Fix the Figma source. |

If a non-colour value legitimately needs to differ between modes, the generator  
must be extended — do not paper over with hand-edited CSS.

### Dark-mode overrides (last-resort)

`darkOverrides[slug]` in `buildThemeProps` patches specific generated props  
with hand-authored `light-dark()` pairs **after** generation. Use only when  
the Figma DTCG export lacks distinct dark values for tokens that visibly need  
them (e.g. active-state surface tints). Each override fires a warning if it  
does not match a generated property — keep the keys in sync with  
`apexToCSS()` output.

## 6\. Anomalies and Conventions

These reflect deliberate choices. Do not "fix" them without coordinating with  
the Figma source.

### 6.1 `critical` → `error`

Figma uses `status/critical/*`; CSS exposes `--sherpa-*-error-*`. Single  
transform in `renameStatus()`.

### 6.2 `surface/status/*` → `surface/context/*`

Figma scopes status colours to the surface category; CSS reframes them as  
contextual surfaces (which can host status _or_ contextual highlights). Same  
applies to `border/status/*`. `content/status/*` follows for text/icon.

### 6.3 Manual aliases injected into every theme

`buildThemeProps` appends a small block of manual aliases (e.g. `--sherpa-border-container-hover`, `--sherpa-surface-container-selected-default`,  
`--sherpa-border-default`, `--sherpa-surface-app-product-bg-default`). These  
are identical across themes by design and end up in `sherpa-theme-base.css`  
via the intersection pass. Keep them theme-agnostic.

### 6.4 Status warning row

`sherpa-status.css` emits the warning row using `-subtle-body` text and  
`--sherpa-icon-context-default-on-color-subtle-body` icon. This is an  
intentional Figma decision — warnings have a softer treatment than the other  
status colours. Documented for future maintainers.

### 6.5 Theme-local brand colours (Phase 3, planned)

Currently `primary-cyan-*` and `primary-blue-*` colour families live in  
`tokens/sherpa-alias.css`. They are scoped to a single theme each and will move into  
the per-theme files (or `sherpa-theme-base.css` if shared) so the alias layer  
stays theme-agnostic. The Figma source must mark them as theme-scoped before  
this can land.

## 7\. Adding Things

### 7.1 Add a new theme

1.  Create `figma-tokens/{NewThemeFolder}/Light.tokens.json` and `Dark.tokens.json` (DTCG format).
2.  Append an entry to `themes.extended` in `figma-tokens/figma-variables.json` with `name`, `slug`, `folder`.
3.  (Optional) Add a `darkOverrides[slug]` block in `buildThemeProps` if the DTCG export is missing dark values for active-state tints.
4.  Run `npm run tokens:generate`.
5.  Add a `<link id="sherpa-theme">` swap target in any consumer that exposes theme picking.

No generator code changes required for a vanilla theme.

### 7.2 Add a new token

If the token is **shared across all themes** → add to `Alias` collection in `figma-variables.json`. It will be emitted in `tokens/sherpa-alias.css`.

If the token is **theme-specific** → add to each theme's DTCG files with the right per-theme value. The generator decides automatically whether it lands in base or per-theme based on whether the values match.

If the token is a **new primitive** → add to `Primitives` in `figma-variables.json` AND to `tokens/primitives.css` (hand-maintained file).

### 7.3 Rename a token

Rename in Figma → re-export → run generator. Update any direct references in  
`components/**/*.css` (do **not** edit generated CSS). Audit  
`darkOverrides[slug]` keys for stale entries.

## 8\. Acceptance

After any change to the generator or token sources, run:

```
npm run tokens:generate          # must complete with no errors
git diff css/styles/             # inspect generated output
```

QA in `index.html` (the playground exposes a theme × mode × density switcher):

*   Switch each theme × each mode (light / dark / auto).
*   Visually verify all hero components.
*   No console errors; no FOUC during theme `<link>` swap.
